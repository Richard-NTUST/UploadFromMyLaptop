# SMO and Automated Workload Testing Architecture

**Date:** 2026-07-13  

## Overview

The SMO works as the higher-level orchestration and management layer. It can't create CPU load by itself. Instead, it coordinates intent, topology info, deployment config, and monitoring data. The real workload is generated by the test service/rApp through E2E traffic runs, mainly iPerf traffic between the server-side 5G data path and the UE.

For our current WINLAB flow, the workload is adjusted by changing test parameters such as offered load, duration, direction, UE model, stabilization time, and the selected deployment mode. 

The rApp receives these parameters -> runs the correct E2E path -> collects logs and throughput data, and finally aligns the results with power data from monitoring systems such as InfluxDB/PDU.

## Main Components

| Component | Role |
|---|---|
| SMO | High-level service management and orchestration layer. Provides inventory/topology context and can host or coordinate rApps. |
| rApp / automated test service | Converts test intent into executable test runs. In our current implementation, this is the FastAPI service exposing `/gnb/run` and `/jobs/<id>`. |
| HPE server | Main runner host. Starts the E2E scripts, launches the iPerf server, stores artifacts, and interacts with Kubernetes/OCloud when needed. |
| OCloud / Kubernetes | Runs the OAI VNF/PNF pods for the OCloud nFAPI path. |
| UE control host (`iapc`) | Controls the Samsung UE through ADB, including attach/re-attach and UE-side iPerf client execution. |
| Test traffic / workload | Generated mainly through iPerf by changing offered bandwidth, duration, direction, and test repetition. |
| Pegatron O-RU | The radio unit under test. Current experiment uses the Pegatron RU `[O]` path. |
| PDU / InfluxDB / CortexDC | Monitoring path for power and infrastructure data. For RU power, we use PDU Outlet 2 `active_power` from InfluxDB. |

## How Workload Is Adjusted

The workload is controlled through rApp request parameters. Example:

```json
{
  "mode": "ocloud",
  "bandwidth": [100, 200, 300],
  "period": 60,
  "gap_time": 2,
  "ue_model": "samsung",
  "uplink": false,
  "settle_time": 30
}
```

These parameters change the test workload as follows:

| Parameter | Meaning |
|---|---|
| `bandwidth` | Offered load in Mbps. A list creates a sweep, for example 100, 200, 300 Mbps. |
| `period` | Duration of each traffic step. |
| `gap_time` | Pause between traffic steps. |
| `uplink` | Selects uplink or downlink direction. |
| `mode` | Selects Bare Metal or OCloud E2E path. |
| `settle_time` | Wait time after deployment or pod readiness before attaching UE and starting traffic. |

So, if the SMO/rApp wants to test different server workloads, it can generate a parameter matrix and run each combination automatically. For example:

- 100 Mbps, 200 Mbps, 400 Mbps downlink
- 60 s per level
- 30 s stabilization time
- repeat each level several times
- collect throughput, logs, UE state, and power data for every run

This is the same idea as a test-case matrix, where the SMO/rApp defines the desired experiment, then the runner executes each permutation.

## Current Lab Flow

1. The operator or SMO/rApp sends a test request to the rApp API.
2. The rApp starts an asynchronous job and records the request.
3. The HPE runner executes either the Bare Metal path or the OCloud path.
4. For OCloud mode, the OAI VNF/PNF pods must be ready in Kubernetes.
5. The UE control host uses ADB to make sure the Samsung UE attaches and receives a `10.45.x.x` address.
6. iPerf traffic is generated for the requested bandwidth and duration.
7. The rApp stores run artifacts: command, request, stdout, UE iPerf JSON, pod logs, throughput CSV, and plots.
8. PDU Outlet 2 `active_power` is exported from InfluxDB for the same UTC time window.
9. A merge script combines throughput and power into one summary table.

## Clarification

The SMO is not the low-level packet generator, workload generation happens through the rApp/test runner and iPerf. The SMO's role is to provide the management framework. The server and UE execute the workload, while InfluxDB/CortexDC/PDU provide the monitoring data used to evaluate the result.

## Summary

The SMO/rApp layer decides what experiment should run, the HPE and UE execute the traffic workload, Kubernetes/OCloud provides the network-function deployment, and InfluxDB/PDU monitoring supplies the power data needed to evaluate throughput-vs-energy behavior.
